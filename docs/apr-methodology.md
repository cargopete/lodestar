# Delegator APR — How Lodestar Computes the *True* Figure

> **TL;DR** — A delegator's APR is rewards ÷ the stake that actually earns them.
> Most dashboards (historically including this one) divided by the *raw*
> delegated total, which silently includes tokens that are thawing and no
> longer earning. That understates APR — sometimes dramatically. Lodestar
> divides by the **active earning base** (`delegatedTokens − delegatedThawingTokens`),
> applies the **Horizon effective cut**, and **cross-checks the denominator
> against the chain** so the number isn't just asserted — it's verified.

---

## The problem: a denominator that counts dead stake

Indexing rewards for delegators are, in essence:

```
APR ≈ annualized delegator rewards / delegated stake × 100
```

The trap is in the denominator. When a delegator undelegates, their tokens
enter a **28-day thaw**. During that window — and, crucially, *even after it
completes, right up until someone calls `withdraw()`* — those tokens:

- **remain inside `delegatedTokens`** (the pool's total), but
- **earn nothing** (thawing stake is excluded from reward distribution).

So if you divide rewards by the raw `delegatedTokens`, you're dividing by a
base that's inflated with stake that isn't pulling any weight. The APR you show
is **too low**. The bigger the thawing pool, the more wrong it gets.

This is exactly the confusion that surfaced on the forums: an indexer's APR
"jumped" with no obvious cause. There was a cause — a large undelegation had
moved a chunk of stake into thawing, shrinking the *earning* base — but the
naïve calculation had been hiding it by keeping the dead stake in the
denominator. The higher figure was the correct one all along.

## The fix: divide by the active earning base

```
activeEarningBase = delegatedTokens − delegatedThawingTokens
```

That single subtraction is **exact** — and a second "fully-thawed" correction
would be a bug, not an improvement. Here's why:

The protocol keeps fully-thawed-but-not-yet-withdrawn tokens inside **both**
`delegatedTokens` **and** `delegatedThawingTokens` until `withdraw()` actually
fires. There is **no time-triggered transition** when the thaw clock hits zero;
passing the deadline only makes tokens *eligible* to withdraw, it doesn't move
them out of the thawing bucket. Therefore `delegatedThawingTokens` is a
superset covering both "still counting down" and "done but un-withdrawn", and
subtracting it once removes all non-earning stake in one clean step. Subtracting
a separately-scanned "fully thawed" amount on top would **double-count** the same
tokens and *under*-state the base.

> Caveat to watch: if a future Horizon contract upgrade adds a separate
> `withdrawable` bucket (discussed in forum thread #6882), `delegatedTokens`
> would then *exclude* thawed tokens and this subtraction logic must be
> re-derived. Until that ships, one subtraction is correct.

## The numerator: the Horizon *effective* cut, not the raw cut

Delegators don't receive all post-cut rewards — they receive the share
generated by *delegated* stake, after the indexer's cut on that portion:

```
delegatorRewards = totalIndexingRewards × delegatedStakeRatio × (1 − indexingRewardEffectiveCut)
```

For a normally-delegated indexer this is algebraically identical to the naïve
`× (1 − rawCut)`. The two **only diverge when an indexer is over-delegated** —
i.e. delegated stake exceeds the delegation-ratio cap. Beyond that cap, the
excess delegated stake earns *nothing*, and `indexingRewardEffectiveCut` rises
above the raw cut to reflect it. Using the raw cut there would over-state
delegator APR. Lodestar uses the subgraph's effective-cut and delegated-stake
ratio (falling back to `1 − rawCut` only when those fields are unavailable), so
over-delegated indexers are scored honestly.

There is no delegation tax adjustment — Horizon removed the 0.5% deposit tax
entirely.

## Verification: we read the chain, not just the subgraph

The subgraph is event-driven and can lag the chain by a few blocks. So for the
denominator we don't merely trust it — we **reconcile** it against the canonical
on-chain state:

```
getDelegationPool(serviceProvider = indexer, verifier = SubgraphService)
    → activeOnChain = pool.tokens − pool.tokensThawing
assert activeOnChain ≈ (delegatedTokens − delegatedThawingTokens) from subgraph
```

- HorizonStaking proxy: `0x00669A4CF01450B64E8A2A20E9b1FCB71E61eF03`
- SubgraphService verifier: `0xb2Bb92d0DE618878E438b55D5846cfecD9301105`

When they match (within a small epsilon for indexing lag), the indexer page
shows a **✓ Chain-verified** badge. When they drift, it says so. This is what
makes Lodestar's figure *authoritative* rather than merely *plausible* — other
dashboards assert a number; we show it agrees with the chain block-for-block.

## Worked example

A real indexer carrying a large recent undelegation:

| Quantity | Value |
|---|---|
| `delegatedTokens` (raw total) | 235,977,861 GRT |
| `delegatedThawingTokens` | 7,481,020 GRT |
| **Active earning base** | **228,496,840 GRT** |

The naïve calculation divides rewards by 235.98M; the correct one divides by
228.50M. Same rewards, smaller (honest) denominator → a **~3.3% higher, and
correct, APR**. On indexers with proportionally larger thaw pools, the gap is
far wider. The on-chain `getDelegationPool` read for this indexer matched the
subgraph to the GRT — zero drift.

## What we deliberately *don't* do

- **No double-subtraction.** One thawing subtraction is exact (see above).
- **No REO gating of APR.** The Rewards Eligibility Oracle (GIP-0079) is read
  and surfaced as an informational badge, but it is **not** folded into the APR
  numerator. Enforcement is governance-gated and, at time of writing, the system
  fails open. We only zero rewards for ineligibility once on-chain enforcement is
  confirmed active — until then, treating it as an APR input would be wrong.
